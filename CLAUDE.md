# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

ProjectUjorm is a lightweight Java 17+ ORM library. It maps database rows to JavaBeans or Records using clean SQL without unnecessary abstraction. Core philosophy: no lazy loading, M:1 relations only, no entity lifecycle management, no magic proxies.

Runtime bytecode compilation achieves performance comparable to hand-written JDBC (<3 MB, zero external dependencies).

## Project Structure

Multi-module Maven project (Java 17, Maven 3.8+):

```
ProjectUjorm (root pom.xml, version 3.0.0)
├── project-m2/
│   ├── ujo-tools/              — SQL builders, JDBC helpers, type system
│   ├── ujo-core/               — Type-safe Key pattern, DomainHandler
│   ├── ujorm-meta-processor/   — APT: generates Meta* classes at compile time
│   ├── ujo-orm/                — ORM engine: EntityManager, SelectQuery, Crud, ResultSetMapper
│   ├── ujo-converter/          — HTML-to-Java element converter
│   ├── ujo-web/                — Web utilities (Spring integration)
│   ├── ujo-arangodb/           — Document database integration
│   └── ujo-xsd/                — XSD tools
└── ujorm3-integration-tests/   — Multi-database ITs (PostgreSQL, MySQL, Oracle, MS SQL Server)
```

Dependency order: `ujo-tools` ← `ujo-core` ← `ujo-orm` ← integration tests.

## Build and Test Commands

```bash
# Build all modules
./mvnw clean install

# Build without tests
./mvnw clean install -DskipTests

# Run unit tests (H2 in-memory, no Docker required)
./mvnw clean test

# Run a single test class
./mvnw test -Dtest=TutorialTest

# Run a single test method
./mvnw test -Dtest=TutorialTest#select_by_criteron

# Run integration tests against real databases (requires Docker, ~6 GB images)
./bin/docker-integration-test.sh

# Or manually for a specific DB
./mvnw verify -P docker-it -pl ujorm3-integration-tests -Dit.test=PostgresTutorialIT
```

Unit tests live in `/project-m2/ujo-orm/src/test/java/org/ujorm/orm/` and extend `AbstractDatabaseTest` (auto-drops and rebuilds H2 schema before each test).

Integration tests live in `/ujorm3-integration-tests/src/test/java/org/ujorm/orm/tutorial/` and use Testcontainers with Spring Boot autoconfiguration.

## Core Architecture Concepts

### The Typed Key Pattern

Keys are type-safe singletons (`Key<Entity, ValueType>`) generated by the APT at compile time. They replace string literals and enable composable, type-checked query DSL.

```java
// Generated by APT from @Table-annotated entity
public class MetaEmployee {
    public static final Key<Employee, Long>   id   = meta.getKey("id");
    public static final Key<Employee, String> name = meta.getKey("name");
    public static final Key<Employee, City>   city = meta.getKey("city");
}

MetaEmployee.name.whereEq("John")  // → Criterion<Employee, Boolean>
```

### The Three Query APIs

**1. EntityManager / Crud** — Simple CRUD by primary key:
```java
crud.insert(entity)
crud.findById(id)
crud.update(entity)
crud.delete(entity)
```

**2. SelectQuery** — Type-safe DSL with automatic JOIN generation:
```java
SelectQuery.run(conn, EMPLOYEE_EM, q -> q
    .column(MetaEmployee.id)
    .column(MetaEmployee.city, MetaCity.name)  // Auto-JOIN on city_id
    .where(MetaEmployee.name.whereEq("John"))
    .toList()
);
```
JOIN type is inferred from `@JoinColumn(nullable=...)`: `false` → INNER JOIN, `true` → LEFT JOIN.

**3. SqlQuery** — Native SQL with parameter binding:
```java
new SqlQuery(conn, "SELECT * FROM employee e WHERE e.name = :name")
    .bind("name", "John")
    .streamMap(mapper)
```

### Annotation Processing (APT)

Entities use JPA/Jakarta annotations; the APT generates `Meta*` classes:

```java
@Table(name = "employee")
public class Employee {
    @Id @Column(name = "id")           Long id;
    @Column(nullable = false)          String name;
    @JoinColumn(name = "city_id")      City city;
}
```

Generated files appear in `/target/generated-sources/`. APT is triggered automatically by `./mvnw clean compile`.

### ResultSetMapper

Maps JDBC `ResultSet` rows to Records or JavaBeans with automatic type conversion. Caches column mappings (limit: 512 distinct queries).

```java
ResultSetMapper<Employee> mapper = ResultSetMapper.of(Employee.class)
    .label("e.id",   MetaEmployee.id)
    .label("e.name", MetaEmployee.name)
    .label("c.name", MetaEmployee.city, MetaCity.name);  // Nested path
```

### Configuration

```java
var config = new Config()
    .setValue(Config.batchSize, 1000)
    .setValue(Config.sqlLogging, true)
    .lock();  // Recommended for thread safety
```

Priority: manual settings > JVM `-Dorg.ujorm.*` > `ujorm-config.properties` on classpath > defaults.

## SQL Logging During Tests

Ujorm logs SQL via `java.util.logging` (JUL) at the level set in `Config.logSqlLevel` (default `FINE`; use `Config.ofSqlInfoWithParams(false)` or `EntityContext.ofSqlInfoWithParams(false)` for `INFO`).

**The catch:** JUL's default `ConsoleHandler` writes to `System.err`, so `./mvnw test | tee log.txt` or `grep SELECT log.txt` finds nothing — the SQL goes to a different stream.

**The fix (already wired in this project):** `Config` reads JUL properties from `ujorm-config.properties` on the classpath on first use (no JVM args, no Surefire config). The test `ujorm-config.properties` in `src/test/resources/` installs `UjormConsoleHandler` which writes to `System.out`:

```bash
# This now works:
./mvnw test -Dtest="*#some_test" 2>&1 | tee log.txt
grep SELECT log.txt
```

`2>&1` is still needed only for other JUL loggers not covered by the file; Ujorm SQL goes to stdout directly.

To add SQL logging to a new test class, construct the context with:
```java
private static final EntityContext CTX = EntityContext.ofSqlInfoWithParams(false);
```

To see bound parameter values too, pass `true`.

**How the mechanism works:**
- `Config` has a private `static final boolean JUL_INITIALIZED = initJulLogging()` field.
- `initJulLogging()` looks for `/ujorm-config.properties` on the classpath via `Class.getResourceAsStream`.
- If found, calls `LogManager.getLogManager().readConfiguration(stream)` — same pattern as how `ujorm-config.properties` is loaded for ORM settings.
- `UjormConsoleHandler` lives in `ujo-tools` (`org.ujorm.tools.logging`) so it has no dependency on `ujo-orm`.
- In production (no JUL properties in `ujorm-config.properties`), the method skips handler setup.

## Common Gotchas

- **No lazy loading:** relations must be explicitly fetched or JOINed in SelectQuery.
- **M:1 only:** for 1:M, query from the "many" side or run a separate query.
- **Transactions:** the ORM does not manage them; use `Connection.commit()` / `rollback()` directly.
- **Self-joins:** use `TableAlias<T>` to create aliased references for self-referencing entities.
- **Multi-tenant:** set `Config.tenantPerDatabaseSchema(true)` when using per-connection schema isolation.
